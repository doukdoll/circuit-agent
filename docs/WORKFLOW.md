# 작업 및 개발 기록 규칙

기능 추가와 트러블슈팅의 판단 근거를 이후 포트폴리오·리뷰에서 확인할 수 있도록 기록합니다. 기록의 중심은 [개발 이력](DEVELOPMENT_HISTORY.md), 실제 실행 절차는 [개발 가이드](DEVELOPMENT_GUIDE.md), 문서 진입점은 [목차](README.md)입니다.

## 브랜치와 승인

1. 작업 트리·기존 변경·저장소 지침을 확인하고, 최신 main을 기준으로 `feat/...`, `fix/...`, `docs/...` 작업 브랜치를 만듭니다. 기존 작업을 이어가는 경우 해당 작업 브랜치를 사용합니다.
2. 수정, 관련 문서 갱신, 변경에 적합한 검증을 완료합니다.
3. 현재 작업에 대한 커밋·푸시 승인이 없다면 결과를 보여주고 승인을 요청합니다. 사용자가 이번 작업에 대해 이미 커밋·푸시를 요청했다면 같은 승인을 반복 요청하지 않습니다. 이전 작업의 승인은 다음 작업에 재사용하지 않습니다.
4. 현재 작업 변경만 커밋하고 작업 브랜치에 일반 푸시한 뒤 main을 대상으로 PR을 작성합니다. main 직접 커밋·푸시와 강제 푸시는 하지 않습니다.
5. PR에는 문제·최종 변경·검증 결과·관련 기록을 적습니다. main 병합은 별도 승인 후 진행합니다.

문서 커밋은 `[docs] 내용`을 사용합니다. 구현 커밋은 기존에 사용한 `[feat] 내용`, `[fix] 내용` 형식에 맞춥니다. 실제 브랜치명·커밋 SHA·PR 링크는 완료 보고에 남깁니다.

## 문서를 갱신하는 시점

| 작업 | 함께 갱신할 기록 |
| --- | --- |
| 기능 추가·동작 변경 | 개발 이력의 문제·설계 선택·변경·검증; 실행법이 바뀌면 개발 가이드 |
| 문제 조사·해결 | 재현 조건·증상·가설·확인된 원인·시도한 대응·최종 해결·재검증·재발 방지 |
| 입력·샘플·Rule 변경 | 출처·기대 결과·개발용 기준·원본 보존 여부; 구현 범위와 요구사항 구분 |
| 새 문서 추가 | docs 목차에 링크 추가 |
| 포트폴리오 정리 | 검증된 결과와 개인 기여·개발 지원·미구현 사항을 대조 |

해당 기능·수정과 기록을 같은 PR에 포함합니다. 실행 명령이나 설명이 틀렸던 경우 성공한 최종 절차로 가이드를 고치고, 개발 이력에는 실패한 시도도 남겨 원인 추적을 가능하게 합니다.

확인한 사실, 사용자 환경의 확인, 추정, 제안을 구분합니다. 테스트 실행 환경·범위·날짜를 남기고, 테스트를 새로 실행하지 않았다면 기존 결과를 재사용한 것이라고 적습니다. 날짜는 Asia/Seoul을 기준으로 기록합니다. 회사 비공개 입력·인증 정보·토큰은 기록하지 않고 공개 자료와 익명화된 증상을 사용합니다.

## 기능 기록 양식

아래 양식을 개발 이력에 복사하여 최신 작업을 추가합니다. 항목은 필요한 만큼 작성하고, 미확정 내용에는 상태를 표시합니다.

```markdown
### YYYY-MM-DD — 기능 이름

- 상태: 구현 완료 / 검증 중 / 제안
- 문제와 목표:
- 구현 범위 및 변경한 파일:
- 설계 선택과 이유:
- 대안 및 선택에 따른 제한:
- 검증: 환경, 실행 명령, 기대 결과, 실제 결과
- 사용자 환경 확인: 확인 방식과 범위
- 관련 근거: 코드·테스트·샘플·커밋·PR 링크
- 다음 작업 및 남은 한계:
```

## 트러블슈팅 기록 양식

```markdown
### TS-NNN — 문제 이름

- 상태: 해결 / 조사 중
- 발생 환경과 재현 절차:
- 증상: 필요한 오류 메시지와 로그
- 가설과 확인 방법:
- 확인된 원인: 증거와 미확정 부분 구분
- 시도한 대응: 결과와 실패한 시도 포함
- 최종 해결: 실제 성공한 명령·코드·설정
- 재검증: 환경, 명령, 기대 결과, 실제 결과
- 재발 방지 및 배운 점:
- 관련 파일·테스트·커밋·PR:
```

작업 완료 시 기록과 실제 변경이 일치하는지, 문서 링크가 유효한지, `git diff --check`가 통과하는지 확인합니다. 문서만 바꾸는 작업에서 이미 완료된 코드 테스트를 다시 실행했다고 적지 않습니다.
