# 웹 구조 및 MySQL 설계 방향

기준일: 2026-10-10, Asia/Seoul. 웹 전환을 위한 설계 기록이며 현재 구현 상태와 구분합니다.

## 결정 상태

| 항목 | 상태 |
| --- | --- |
| 웹으로 사용 | 사용자 요구 |
| DB: MySQL | 사용자 선택 확정 |
| BE: Spring Boot + Java 21 | 구현 제안; 기존 Java 검사 코드 재사용 |
| FE: React + TypeScript + Vite | 구현 제안; 프론트 기술 최종 확정 전 |
| 로컬 DB: Docker Compose | 실행 환경 제안 |
| MySQL 버전: 8.4 LTS | 버전 제안; 실행 환경에서 확인 후 확정 |

현재 저장소에는 Java CLI 파서·기본 검사·HTML/JSON 보고서가 있습니다. Spring Boot API, FE, DB 연결, Docker Compose는 아직 구현하지 않았습니다. 현재 실행 방법은 [개발 가이드](DEVELOPMENT_GUIDE.md)에 있습니다.

## MySQL을 선택한 이유

프로젝트·파일·검사 이력·사람 검토는 관계형 데이터이며, 외래 키와 트랜잭션으로 관리할 수 있습니다. Rule마다 달라지는 계산값·근거는 MySQL JSON 컬럼으로 보관할 수 있습니다. 현재 기능에는 PostgreSQL 전용 기능이 필수 조건으로 없습니다.

초기 제안에서는 JSONB 활용을 이유로 PostgreSQL을 추천했으나, 사용자가 MySQL을 선택했으므로 MySQL을 기준으로 후속 설계를 진행합니다. 사용자의 MySQL 숙련도나 기존 운영 경험은 확인하지 않았습니다.

## 저장 책임

| 데이터 | 제안 저장 방식 |
| --- | --- |
| 프로젝트 | 이름·설명·생성 시각을 테이블에 저장 |
| 업로드 파일 | 원래 파일명·저장 위치·해시·크기를 테이블에 저장; 실제 내용은 파일 저장소 |
| Rule 버전 | 검사 당시 기준을 식별하는 버전·내용·출처 보존 |
| 검사 실행 | 입력 파일·Rule 버전·실행 상태·시작/종료 시각·요약 저장 |
| 검사 결과 | 인스턴스·Rule·판정·이유는 컬럼, 변동 계산값·근거는 JSON 후보 |
| 사람 검토 | 자동 결과와 연결된 의견·확인 상태·시각·재검증 연결 저장 |
| HTML 보고서 | 파일 저장소에 저장하고 DB에는 식별·위치 정보 저장 |

판정·실행 시각처럼 자주 필터링하는 값은 일반 컬럼과 인덱스로 다룹니다. 입력 파싱용 부품·핀·넷 전체를 처음부터 DB 테이블로 옮기는 것은 초기 필수 범위로 두지 않습니다. 구체적인 테이블·관계·JSON 구조는 API 계약과 함께 확정합니다.

개발 환경에서는 Docker Compose로 MySQL 컨테이너를 띄우는 방식을 제안합니다. DB 데이터는 Docker 볼륨으로 보존하고, 업로드·보고서 저장 위치도 별도로 유지합니다. 실제 비밀번호는 Git에 올리지 않으며 `.env.example`에는 변수 이름과 예시만 기록합니다. 별도의 물리 DB 서버를 초기 개발 조건으로 두지 않습니다.

## UI·UX 흐름

1. 프로젝트 목록에서 프로젝트를 생성하거나 선택합니다.
2. 프로젝트 상세에서 파일과 검사 이력을 확인합니다.
3. QCV 업로드 → 지원 Rule 선택 → 명시적 DNI 설정 → 검사 실행 순서로 진행합니다.
4. 실행 상태를 확인하고, 완료 후 결과 요약·판정별 목록을 표시합니다.
5. 결과 행을 선택하면 입력값·계산식·기준·연결·원문 근거를 상세 패널에서 확인합니다.
6. 검토 필요 항목에 의견을 남기고, 추가 정보가 확보되면 별도 재검증을 연결합니다.

결과 화면에는 검사 대상·판정 완료·위반·검토 필요·입력 오류·DNI 제외 개수를 표시합니다. 색상과 함께 텍스트 상태를 제공하고, FAIL/NEEDS_REVIEW 필터로 먼저 확인할 항목을 찾도록 합니다. 업로드 화면에는 현재 지원 문법과 파일 오류의 이유·위치를 표시합니다. 아직 지원하지 않는 BOM 입력은 구현 전까지 필수 업로드로 요구하지 않습니다.

실행 상태(대기 중·검사 중·완료·실행 오류)와 검사 판정(PASS·FAIL·NEEDS_REVIEW)을 구분합니다. 정상적으로 완료된 검사에도 FAIL이 있을 수 있습니다. 사람의 확인은 자동 판정을 덮어쓰지 않고, 자동 결과·검토 의견·재검증 결과를 따로 남깁니다.

전체 회로 편집기보다 결과 근거를 확인하는 화면을 먼저 구현합니다. 장시간 검사에서는 응답을 기다리는 대신 실행 ID로 상태·결과를 조회하는 방식을 제안합니다. 비동기 실행과 서버 재시작 시 처리 정책은 구현 단계에서 확정합니다.

## 후속 구현 순서

1. 디렉토리 정리 및 기존 CLI·테스트 실행 경로 유지
2. Spring Boot와 MySQL 연결, DB 변경 이력 도입
3. 프로젝트·파일 업로드·검사 실행·결과 조회 API
4. FE에서 정상·위반·값 누락 사례의 업로드부터 결과 확인까지 연결
5. 검사 이력 및 사람 검토·재검증 저장

구현이 시작되면 [개발 이력](DEVELOPMENT_HISTORY.md)에 실제 변경·검증을 기록합니다. 현재 MySQL 선택은 설계 결정이며 DB가 이미 실행되거나 웹 기능이 완성됐다는 의미가 아닙니다.
